# P3 코드 리뷰 요청·받기

> 출처: [obra/superpowers](https://github.com/obra/superpowers) `requesting-code-review` + `receiving-code-review` (commit `2ce8aa1`, MIT). 2조 `layer-reviewer` 에이전트와 담당자 계약 구조에 맞게 바꿨다.
> 우선순위: `CLAUDE.md` > `code-rules` > `p3-orders` > 이 파일.

## A. 리뷰 요청
**언제 (필수):** 한 계층·한 기능을 마쳤을 때, 커밋·PR 전, 재고·주문 상태·잠금을 바꿨을 때.

1. 검토 범위를 정한다: 바뀐 파일 목록(`git diff --stat`), 검토하지 않을 파일(진행 중인 다른 작업).
2. `layer-reviewer` 에이전트에 **결론이 아니라 코드와 규칙 위치**를 준다:
   - 규칙: `CLAUDE.md`, `.claude/skills/code-rules`, `.claude/skills/p3-orders`, `docs/products/P2_STOCK_REPOSITORY.md` 2장
   - 꼭 볼 것: commit/rollback 위치, 잠금 순서, 재고는 P2 함수로만, 실패 시 부분 저장, 서버 쪽 소유권 검사, 비밀값
   - 읽기 전용으로 하고 파일:줄과 심각도로 보고하게 한다.
3. 결과 처리: 치명·중요는 다음 작업 전에 고친다. 사소한 것은 기록해 둔다.

## B. 리뷰 받기
**원칙:** 고치기 전에 검증한다. 모호하면 묻는다. 듣기 좋은 말보다 기술적으로 맞는 게 우선이다.

1. 끝까지 읽는다 → 2. 내 말로 요구를 다시 정리한다 → 3. 코드·문서로 사실인지 확인한다 → 4. 맞으면 고치고, 틀리면 근거를 들어 반대한다 → 5. 한 항목씩 고치고 각각 테스트한다.

- **말로만 동의하지 않는다**: "좋은 지적이에요!" 대신 무엇을 어떻게 고쳤는지 쓴다.
- **불분명한 항목이 하나라도 있으면 먼저 묻는다.** 이해한 것만 먼저 고치면 나중에 엇갈린다.
- **에이전트 리뷰도 검증한다**: 예) "500이 {code,message}가 아닐 수 있다" → `core/errors.py`의 전역 처리기를 직접 확인하고 판단한다.
- **담당자 영역 의견**: P1(`core/`·`main.py`·인증), P2(재고·상품), P4(관리자)에 관한 요청은 그 담당자의 계약 문서·답변을 기준으로 판단하고, 내 폴더 밖은 직접 고치지 않고 요청한다.
- **반대해야 할 때**: 지금 코드를 깨뜨림, 계약(`p3-orders`, P2 계약)과 충돌, 쓰지 않는 기능(YAGNI), 리뷰어가 맥락을 모름. 근거(파일:줄, 테스트)를 붙여 말한다.
- **내가 틀렸으면**: "확인해 보니 맞았어요. X 때문이에요. 고쳤어요."처럼 사실만 짧게 말한다.

## 고치는 순서
1. 막는 문제(깨짐·보안·재고 정합성) → 2. 간단한 수정 → 3. 복잡한 수정. 각 수정마다 `tests/orders`를 다시 돌린다.

## GitHub PR 코멘트에 답할 때
- 해당 코멘트 스레드에 답한다(전체 코멘트로 흩뿌리지 않는다).
- 고친 커밋 해시와 확인 결과(테스트 숫자, DB 전→후)를 함께 적는다.
