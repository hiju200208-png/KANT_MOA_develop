## 슬라이드 1. 인수 당시 → 지금

| | 인수 당시 (3조) | 지금 (2조) |
|---|---|---|
| 관리자 기능·역할 | 없음. 상품·재고·공지를 마이그레이션 SQL로만 관리, USER/ADMIN 구분 없음 | 관리자 API 12개 + 화면 5개(로그인·대시보드·상품 목록·상품 상세·공지), 라우터 전체에 `require_admin` |

## 슬라이드 2. 구조와 요청 흐름

```
관리자 화면 → src/services/admin/*.ts → POST /admin/products/{pid}/variants/{vid}/stock-adjustments
  → presentation(router: require_admin, 요청 검증, 예외→HTTP)
  → application(AdminStockService: 잠금 조회 → 규칙 → 저장 → commit / 실패 시 rollback)
  → domain(StockAdjustment 입력 규칙, P2 재고 규칙은 그대로 호출)
  → infrastructure(P2 ProductRepository 어댑터, ORM 재사용) → PostgreSQL
```

- 재고 규칙(0 미만 불가, 증감)은 P2 한 곳에만 둠. P4는 호출만 하고 예외를 409·422로 바꿈
- 도메인은 FastAPI·SQLAlchemy를 import하지 않음 → DB 없이 규칙 테스트

## 슬라이드 3. 만든 기능과 업무 규칙

- 상품 목록·상세: 숨김 상품 포함, 옵션 재고 합계·품절 계산, 검색·필터·정렬(최신/재고 적은 순/이름)·페이지
- 재고 조정: 증감 0 불가, -10000~10000, 사유 100자. 부족하면 409, 잘못된 값 422
- 판매 상태 변경: on_sale / sold_out / hidden. 목록에서 여러 개를 한 번에 변경(1~100개, 없는 상품이 섞이면 404 + 전부 rollback)
- 대시보드: 전체·판매중·품절·숨김·재고 없음·재고 부족 집계, 카드를 누르면 같은 조건의 목록으로 이동
- 공지 등록·수정·삭제, 대표 이미지 교체(jpeg·png·webp, 5MB, 파일 시그니처 검사)
- 관리자 로그인: P1 `/auth/login`·`/auth/me`로 ADMIN만 입장, 로그아웃은 토큰 블랙리스트

## 슬라이드 4. 시연 순서

1. Swagger: 토큰 없이 `/admin/dashboard` → **401**, 일반 회원 토큰 → **403**
2. `/admin/login` 관리자 로그인 → 대시보드 카드(재고 부족 배너)
3. 재고 부족 카드 → 재고 적은 순 목록
4. 상품 상세에서 재고 +5 → **DB 12 → 17**, -1000 → **409, DB 17 그대로**
5. 목록에서 2개 선택 → 숨김 일괄 변경 → **on_sale 2 → hidden 2**, 없는 상품이 섞이면 404이고 상태 그대로
6. 공지 등록 → 삭제 (**notices 0 → 1 → 0**)
7. 로그아웃 → 같은 토큰으로 호출 → **401** (블랙리스트 1행)

## 슬라이드 5. 트러블슈팅

- 관리자 재고 수정과 P3 결제가 같은 옵션 행을 동시에 바꾸면 한쪽 값이 덮어써질 수 있음 → 값 덮어쓰기 대신 증감 방식 + 잠금 조회(id 오름차순)를 P2 함수 한 곳으로 통일
- P1·P2 코드가 나오기 전에 구현해야 했음 → 서비스가 기대하는 모양(포트)만 먼저 정의하고 가짜 저장소로 테스트, 이후 P2 함수·ORM에 연결
- Windows 앱 제어 정책이 SQLAlchemy `.pyd`와 uv python을 차단 → `.pyd`만 지우고 `--no-sync` 실행, 또는 막히지 않은 python으로 별도 가상환경 사용. 원인과 해결을 팀 채널·문서에 기록
- main 병합 시 상재님 PR과 `admin/client.ts` 충돌 → 공용 `session` 모듈을 그대로 쓰도록 맞춰 로그인 상태 이벤트도 일반 화면과 공유
