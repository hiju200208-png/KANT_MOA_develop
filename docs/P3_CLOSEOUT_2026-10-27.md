# P3 여름 — 제출 전 검증·인수 기록 (2026-10-27)

## 상태

P3 장바구니·비회원 병합·배송지·주문·바로 구매·모의 결제·취소 코드는 main에 통합되어 있다. 이번에는 주문 내역이 100건 이후 누락되는 프론트 오류를 보완하고, 최신 main `65bf153` 반영 후 아래 검사를 실행했다. 이번 수정은 PR 리뷰·CI·병합 후 팀 코드에 반영한다.

## 수정

기존 `getOrders()`는 `/orders?page=1&size=100`만 조회했다. 화면의 전체·상태별 목록과 개수가 최신 100건에 한정되는 원인이었다. `readOrderHistory`가 API 상한 100을 지키며 다음 페이지를 순서대로 조회하고, 마지막 페이지 또는 빈 페이지에서 멈추도록 변경했다. 뒷페이지 요청 실패는 부분 목록을 성공으로 반환하지 않고 화면의 기존 오류 처리로 전달한다.

0·1·100·101·250건, 오래된 취소 주문, 뒷페이지 실패, 조회 중 빈 페이지의 회귀 테스트 7개를 추가했다. 기존 1페이지 동작에서는 4개 실패를 확인한 뒤 수정했다. 읽기 전용 코드 리뷰에서 차단 사항 없음. 페이지 사이에 주문이 동시에 추가·삭제될 때 완전한 스냅샷 일관성을 보장하는 변경은 아니다.

## 화면·DB 재확인

기존 개발 DB와 공용 DB를 사용하지 않았다. 별도 일회용 PostgreSQL + 최신 로컬 FastAPI + 프론트 사본에서 가상 계정·가상 배송지·검증 상품으로 수행했다. 재고·주문 변경은 이 전용 환경에서만 실행했다.

| 시나리오 | 화면 / API 결과 | DB 전 → 후 |
| --- | --- | --- |
| 비회원 상품 2개 담기 | 장바구니 2개 안내 | cart_items 0 → 0, 재고 5 → 5 |
| 로그인·비회원 병합 | 로그인 상태, 상품 2개 | cart_items 0 → 1행(quantity=2), 재고 5 → 5 |
| 첫 배송지 생성 | 기본 배송지 표시 | addresses 0 → 1, 기본 true |
| 배송지 수정 | 수정된 배송지명 | 동일 id의 label 변경, 행 수 1 → 1 |
| 두 번째 주소·기본 전환 | B 기본, A 일반 | A true/B false → A false/B true |
| 기본 B 삭제 | 남은 A가 기본 | 2행 → 1행, A false → true |
| 장바구니 주문·모의 결제 | 결제 완료, 상품 40,000 + 배송비 3,000 = 43,000원 | 재고 5 → 3, orders paid·paid_at, cart_items 1 → 0 |
| 상세 새로고침 | 결제 완료 유지 | 조회만, 재고 3 유지 |
| 취소 API | cancelled | 재고 3 → 5, cancelled_at 저장, 장바구니 0 유지 |
| 실제 주문 101건 | 전체 101·결제 대기 100·취소 1, 주문 카드 101개 | DB 101건, API 1페이지 100 + 2페이지 1. 가장 오래된 취소 주문 표시 |
| 화면 로그아웃 | 홈으로 이동 | token_blacklist 0 → 1, 재고 5 유지 |

취소 버튼 클릭의 네이티브 확인창은 브라우저 자동화 도구가 처리하지 못했다. 취소 API의 결과·DB 복구와 기존 실제 DB 자동 테스트는 확인했으며, 이번 실행을 '취소 버튼부터 끝까지 브라우저 성공'으로 표현하지 않는다.

임시 프론트는 기존 Next 서버와 충돌을 피하기 위한 사본이며 webpack으로 구동했다. CSS가 정상 적용되지 않은 상태여서 이번 화면 확인은 기능·텍스트·응답/DB 검증이고, 제출 화면 디자인 검수로 보지 않는다. 실행 중 설치된 Next 버전의 보안 업데이트 알림도 나타났으므로 의존성 정리는 팀 공통 환경 작업으로 별도 확인한다.

1. 로컬 API와 프론트가 같은 전용 DB를 사용하는지 확인한다.
2. 비회원 장바구니 2개 → 로그인 → 병합된 수량을 보여 준다.
3. 배송지 선택 → 43,000원 모의 결제 → 상세 새로고침 유지.
4. 재고 감소(5→3)와 장바구니 삭제를 DB로 보여 준다.
5. 실제 브라우저에서 취소 확인창을 직접 승인하고 재고 복구(3→5)를 보여 준다.
6. 로그아웃 후 보호 API 401을 보여 준다. API 통합 자동 테스트에도 블랙리스트 검증이 있다.

## Slack 확인 뒤 승인된 추가 기능 — 관리자 주문·배송

최종 범위는 기존 100건 누락 수정에 관리자 주문·배송을 포함한다. 사용자 승인으로 P3가 구현했고 P4 상품·재고 기능은 변경하지 않았다. 화면 `/admin/orders`, API `/orders/admin`(GET) 및 `/orders/admin/{id}/shipping`(PATCH). 결제·배송을 분리하고 paid만 순방향 배송한다. 발송 후 일반 취소는 거부한다.

검증: 기본423 passed/90 skipped, 실제 DB322 passed/5 skipped, 프론트43 passed·typecheck/lint 통과. ADMIN 권한·상태 전이·commit 실패rollback·취소/발송 경합·검색/페이지 경계를 포함한다.

전용 DB 브라우저: pending은 배송 버튼 없음. paid는 준비→발송→배송 완료를 확인 창에서 확정하고 필터로 조회했다. order_shipments 0→1, 발송·완료 시각/관리자 저장, 재고4→4·결제paid 유지. 신규 UI는 Turbopack 프론트 사본에서 CSS가 정상 적용된 화면으로 확인했다. 앞 절의 webpack/CSS 제한은 이전 검사에만 해당한다.

공용 DB는 미적용. revision4c726d1a91ab은 최초baseline3f 이후에 적용한다. 마이그레이션보다 먼저 신규 코드를 배포하면 취소 API가 배송 테이블을 읽지 못하므로 순서를 지켜야 한다. 백업 확인은 서버 인증 실패로 수행하지 못했다. 팀 채널 전송·병합·공용 적용은 아직 하지 않았다.
